KQL

Q What is KQL?

KQL stands for Kusto Query Language.

It is a query language used to search, filter, analyze, and visualize data stored in Microsoft services such as:

• Microsoft Sentinel — SIEM and threat hunting.

• Microsoft Defender XDR — endpoint and security investigations.

• Azure Monitor and Log Analytics — system, application, and infrastructure logs.


Think of KQL as SQL-like querying for security logs. 
You ask questions about log data, and KQL returns the matching records.

For example, a SOC analyst might ask:

◇ Which users had failed login attempts?
◇ Which IP addresses generated suspicious activity?
◇ Which devices executed PowerShell?
◇ Which users logged in from unusual locations?
◇ How many security alerts occurred in the last 24 hours?
KQL helps answer these questions.




Start with these queries. They use Microsoft Sentinel log tables, so run them in a workspace that has the relevant tables and data.

1. How to run the queries
Keep your complete let SecurityLogs = datatable(...) [...] ; block at the top. Below it, replace SecurityLogs | take 100 with one practice query at a time.
For example:
SecurityLogs
| where Status == "Failed"
| project TimeGenerated, User, SrcIP, Device, Severity
| order by TimeGenerated desc

This displays failed logins with their timestamps, users, source IPs, devices, and severity.
Important: Your table is simulated training data. IP addresses such as 203.0.113.25 and 198.51.100.40 belong to ranges reserved for documentation, so treat the results as lab exercises rather than evidence of real attacks.

6. Create new columns with extend, case, and iff

41. Create a readable event category
SecurityLogs
| extend EventCategory = case(
    EventID == 4625, "Failed Logon",
    EventID == 4624, "Successful Logon",
    EventID == 4688, "Process Creation",
    EventID == 4663, "Object Access",
    "Other Event"
)
| project TimeGenerated, User, EventID, EventCategory



42. Flag failed logins
SecurityLogs

    Status == "Failed", "Investigate", "Normal")

43. Create a byte-size category
SecurityLogs

    Bytes >= 75000, "Very High",
    Bytes >= 10000, "High",
    Bytes >= 2000, "Medium",
    "Low"

| project User, Device, Bytes, TrafficLevel



44. Convert bytes to kilobytes
SecurityLogs

| project User, Process, Bytes, KB



45. Combine user and device names

46. Extract the IP's first three octets

47. Classify events using case()

8. SOC threat hunting queries
These queries use your dataset to investigate suspicious activity. A detection result is a lead for investigation, not proof of compromise.

61. Identify repeated failed logins from an IP
SecurityLogs
| where EventID == 4625
| summarize
    Failures = count(),
    TargetUsers = make_set(User),
    Devices = make_set(Device)
    by SrcIP
| where Failures >= 3
| order by Failures desc

SOC use: identify possible password guessing.


62. Find accounts targeted by multiple IPs
SecurityLogs
| where Status == "Failed"
| summarize
    Attempts = count(),
    SourceIPs = make_set(SrcIP),
    UniqueIPs = dcount(SrcIP)
    by User
| where UniqueIPs > 1



63. Find accounts with failed and successful logins
let FailedUsers =
    SecurityLogs
    | where EventID == 4625
    | distinct User;
let SuccessfulUsers =
    SecurityLogs
    | where EventID == 4624
    | distinct User;
FailedUsers
| join kind=inner (SuccessfulUsers) on User

This identifies users with both event types somewhere in the dataset. It does not prove that a successful login occurred after a failure.


64. Look for PowerShell execution

| project TimeGenerated, User, SrcIP, Device, Severity



65. Find PowerShell activity on each device

    by Device



66. Identify high-byte network events

| project TimeGenerated, User, SrcIP, Device, Process, Bytes
| order by Bytes desc

SOC use: investigate unusually large recorded byte values. The data alone does not establish data exfiltration.

73. Find accounts with at least three failures in any five-minute window
SecurityLogs
| where EventID == 4625
| summarize Failures = count()
    by User, bin(TimeGenerated, 5m)

This uses fixed five-minute buckets, not a sliding five-minute window.


74. Find the time between consecutive events per user
SecurityLogs
| sort by User asc, TimeGenerated asc
| serialize
| extend PreviousUser = prev(User),
         PreviousTime = prev(TimeGenerated)
| where User == PreviousUser
| extend SecondsBetween =
    datetime_diff("second", TimeGenerated, PreviousTime)
| project User, PreviousTime, TimeGenerated, SecondsBetween

3. Advanced: join, union, let, parse, serialize.

5. Sentinel implementation: work with real tables such as SecurityEvent, SigninLogs, DeviceProcessEvents, and CommonSecurityLog when the relevant data sources are connected and populated.



Remember: your custom SecurityLogs table exists only within the query that defines it. In Microsoft Sentinel, real log tables must be ingested and available in your workspace. Also, SecurityEvent and SigninLogs use different schemas, so adapt each query to the actual columns available
